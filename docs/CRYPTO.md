# Шифрование, хранение и миграция v2

Статус: **утверждено** (2026-11-25, ред. 2 после двух кругов ревью). Закрывает
задачи роадмапа 3.2–3.4. Основание: [SECURITY_AUDIT.md](SECURITY_AUDIT.md) (C1–C4, D1–D4, S3–S4, L3)
и решения пользователя: новый ключ вместо старого; вход на выбор (пароль / биометрия / без
проверки); регистрация открыта (друзья); APK-only.

## 1. Модель угроз

Защищаемся от:
1. **Сервера и всех, у кого есть доступ к Firebase** (утечка, ошибка в правилах, как было с
   `if true`). Сервер видит только шифротекст: не может прочитать записи, изменить их содержимое
   или переставить их между документами и аккаунтами (GCM-тег + AAD).
2. **Человека с разблокированным телефоном**, в режимах «пароль» и «биометрия».
3. **Утечек на устройстве**: скриншоты, буфер, логи (5.3; здесь только ключи).

**Ограничения (честно):**
- Сервер (или тот, кто получил запись в Firestore) может **удалить** запись или **откатить** её к
  более старой версии того же документа: старый шифротекст с тем же `entryId` пройдёт проверку
  тега. То же касается старого `wrappedDek`. От удаления защищают правила (§5) и бэкапы, от отката
  не защищаемся (для личного менеджера паролей приемлемо).
- Серверу видны: email, количество записей, `updatedAt` каждой записи, примерная длина записи
  (смягчено паддингом, §3).
- Не защищаемся от заражённого или рутованного телефона во время работы приложения и от режима
  «без проверки» (осознанный выбор).

## 2. Ключи

```
Recovery Key (RK, 256 бит, CSPRNG) ── у пользователя: бумага / офлайн
   │ HKDF-SHA256(ikm = RK, salt = uid, info = "pm/v2/kek")
   ▼
KEK ── AES-256-GCM оборачивает ──► DEK (Data Encryption Key, 256 бит, CSPRNG)
                                      │ AES-256-GCM
                                      ▼
                                   записи
```

- **RK (ключ восстановления).** Генерируется на устройстве из CSPRNG (`IRandom` → `ExpoRandom` → `expo-crypto.getRandomValues`; `getRandomBytes` не использовать: в `__DEV__` он откатывается на `Math.random`).
  Показывается как текст и QR. На сервер **никогда** не передаётся. Нужен на новом устройстве, после
  сброса локальной обёртки и как запасной вход.
- **DEK (ключ данных).** Случайный, им шифруются записи. В Firestore только обёрнутый:
  `wrappedDek = AES-GCM(KEK, DEK, AAD = "pm/v2/dek|" + uid + "|" + rkVersion)`.
- **Проверка ключа (C4):** успешный разворот `wrappedDek` (тег GCM сошёлся) и есть проверка RK.
  Отдельное контрольное значение не нужно. Опечатки ловит контрольная сумма RK (§2.1) ещё до
  обращения к серверу.
- **Зачем два уровня:**
  - *Перевыпуск RK* (потерял бумагу, но телефон под контролем): новый RK переоборачивает **тот же**
    DEK, записи не перешифровываются. Это помогает, только если тот, кто нашёл старый RK, не видел
    `wrappedDek`.
  - *Компрометация* (RK утёк и, возможно, был доступ к Firestore): **смена DEK**, то есть новый RK +
    новый DEK + перешифровка всех записей. При десятках записей это дёшево, процедура та же, что в
    миграции (§6, транзакционно).
- `salt = uid` привязывает KEK к аккаунту. Для равномерно случайного 256-битного RK это допустимо.

### 2.1 Формат ключа восстановления
- Кодируется поток `RK (32 байта) ‖ checksum` в **Crockford Base32**, где checksum = первые 20 бит
  SHA-256(RK). 276 бит → **56 символов**, 14 групп по 4: `7KQ2-M9XD-…-H3TZ`. Последние 4 бита
  заполнения нулевые; декодер **отвергает** ненулевое заполнение (одна строка ↔ один ключ).
- Алфавит без I, L, O, U. При вводе: регистр не важен, дефисы и пробелы игнорируются, `O→0`,
  `I/L→1`; `U` и прочие символы вне алфавита дают ошибку «недопустимый символ».
- **QR:** `pmrk1:` + те же 56 символов, один формат и один парсер для QR и ручного ввода.
- **Сохранение (решение пользователя: удобно скопировать, а не переписывать на бумагу):**
  - кнопка **«Копировать»**: в буфер с флагом `EXTRA_IS_SENSITIVE` (Android скрывает превью),
    буфер очищается через 2 минуты и при уходе с экрана;
  - кнопка **«Сохранить в файл»**: `.txt` через системный диалог сохранения;
  - QR остаётся для переноса на другое устройство камерой. Скриншоты экрана запрещены
    (`FLAG_SECURE`), поэтому сохранить ключ скриншотом в галерею нельзя (S1);
  - подсказка: хранить ключ отдельно от Google-аккаунта, к которому привязан Firebase (например,
    в другом менеджере паролей или в заметках другого сервиса).
- **Подтверждение сохранения (6.4):** следующий экран просит **вставить или ввести весь ключ из
  места, куда вы его сохранили**. Буфер к этому моменту уже очищен, поэтому подтверждение доказывает,
  что ключ действительно сохранён. Проверяется весь ключ (контрольная сумма + точное совпадение).

## 3. Шифрование записей

- **AES-256-GCM**, ключ = DEK, **nonce 96 бит из `expo-crypto`** на каждое шифрование.
- **AAD** = `"pm/v2/entry|" + uid + "|" + entryId`. `entryId` (UUID v4 из `expo-crypto.randomUUID`)
  генерируется **до** шифрования и сразу используется как ID документа, в том числе при миграции.
- Шифруется весь объект (L3):

```ts
type EntryPayloadV2 = {
  readonly title: string
  readonly login: string
  readonly password: string
  readonly url?: string
  readonly notes?: string
  readonly favorite?: boolean
  readonly createdAt: number // ms epoch
  readonly updatedAt: number
}
```

- Перед шифрованием JSON дополняется пробелами до кратного **64 байтам**, чтобы скрыть точную
  длину пароля и заметок.
- Формат: `v2.<base64url(nonce)>.<base64url(ciphertext‖tag)>`. Неизвестная версия → явная ошибка.
- **Библиотеки:** `@noble/ciphers` (gcm), `@noble/hashes` (hkdf, sha256, scrypt). Это аудированные
  библиотеки на чистом JS. **Запрещено** использовать noble `randomBytes`/`managedNonce`: им нужен
  `crypto.getRandomValues`, которого в Hermes нет. Вся случайность (RK, DEK, nonce, соль, UUID)
  берётся только из `expo-crypto` через интерфейс `IRandom`.
- Интерфейсы (DI, см. ARCHITECTURE.md): `ICryptoService` (AEAD, HKDF), `IKdf` (парольный KDF,
  можно заменить на нативный), `IRandom`, `ILegacyDecryptor` (только расшифровка CryptoJS:
  `Salted__`, `EVP_BytesToKey`/MD5, AES-256-CBC, нужен только для миграции).

## 4. Ключ на устройстве и режимы входа

Хранилище: `expo-secure-store` (Android Keystore) за интерфейсом `ISecureStorage`. Режимами,
обёртками, счётчиком попыток и авто-блокировкой управляет `VaultLockService` (entities/session).

| Режим | Что лежит в SecureStore | Разблокировка |
|-------|-------------------------|---------------|
| **Биометрия** | DEK с `requireAuthentication: true` (ключ Keystore привязан к биометрии) | Отпечаток. **Запасной вход: только RK** (решение 5.3: при включении биометрии локальная обёртка паролем удаляется, чтобы не держать два способа входа) |
| **Пароль приложения** | Локальная обёртка DEK (формат ниже) | Пароль (≥ 6 символов, можно цифры) |
| **Без проверки** | DEK без аутентификации | Сразу (предупреждение при включении) |

**Локальная обёртка (режим «пароль»):**
```
{ v: 1, kdf: "scrypt", N, r, p, salt: b64(16 байт), wrapped: "v2.<nonce>.<ct>" }
AAD = "pm/v2/local|" + uid + "|password"
```
Параметры KDF хранятся **вместе** с обёрткой, поэтому их можно менять без потери доступа:
новые параметры применяются при следующей смене пароля или режима (автоматического перевыпуска при входе нет).

**KDF.** scrypt (`r=8, p=1`). Целевое время 0,5–1 с на телефоне пользователя. **Замер (5.3, release, эмулятор Pixel 9 Pro): чистый JS в Hermes N=2¹⁴ — 4,7 с, N=2¹⁵ — 9,5 с, поэтому KDF нативный** (`modules/pm-kdf`, Kotlin + BouncyCastle `SCrypt`, `NativeScryptKdf`): N=2¹⁴ — 195 мс, 2¹⁵ — 399 мс, 2¹⁶ — 780 мс, контрольный вектор RFC 7914 на устройстве совпал. `NobleScryptKdf` (JS) остаётся для тестов. Параметры подбираются при включении режима (`calibrateKdf`, 2¹⁴…2¹⁶, цель ≈700 мс) и хранятся вместе с обёрткой. Исходная формулировка: нужен **замер в
прототипе (4.x)**: N=2¹⁷ требует 128 МиБ, а Hermes без JIT заметно медленнее V8. Если чистый JS не
даёт ≥ 2¹⁵ за ~1 с, через `IKdf` подключается нативный KDF (`react-native-quick-crypto` scrypt либо
Argon2id). Перебор вне устройства затруднён и без того: обёртка лежит в Keystore.

**Лимит попыток:**
- Счётчик `attempts+1` и время записываются в SecureStore **до** проверки пароля и сбрасываются
  только после успеха. Если убить приложение во время KDF, попытка всё равно засчитана.
- Задержки: 0, 0, 0, 30 с, 1 мин, 5 мин, 15 мин, затем 1 ч на каждую попытку. Если системное время
  оказалось раньше сохранённого (перевод часов назад), сохранённое время заменяется текущим и
  задержка отсчитывается заново (без вечной блокировки при переводе часов на год назад).
- **Стирания ключа после N ошибок нет.** Оно позволило бы любому, у кого телефон в руках, за 10
  попыток уничтожить доступ, а при потерянном RK и данные. Растущих задержек и Keystore достаточно.

**Прочее:**
- Смена режима или его отключение только после подтверждения текущим способом.
- **Сброс биометрии в системе** (новый отпечаток): Keystore аннулирует ключ. Приложение просит
  RK (запасной вход биометрии только он, решение 5.3) и заново выбирает режим.
- **Авто-блокировка (S3):** уход в фон дольше grace-периода (30 с по умолчанию) или бездействие.
  Ссылка на DEK обнуляется (`Uint8Array.fill(0)`), кэш расшифрованных записей и state очищаются,
  показывается экран блокировки. Полного стирания из памяти JS гарантировать нельзя (строки
  иммутабельны), поэтому расшифрованные значения держим как можно меньше времени. В режиме «без
  проверки» не применяется.
- **Android Auto Backup:** данные SecureStore исключаются из бэкапа (`allowBackup=false` /
  `dataExtractionRules`), иначе восстановленные значения не расшифруются.
- Выбор режима при первом запуске (5.3): после ввода RK (`VaultRecoveryService`) экран «Настройка защиты».
- **Известные ограничения (5.3):** перевод часов **вперёд** обходит задержки (монотонных часов
  между запусками нет); бездействие считается по касаниям экрана, поэтому долгий ввод с
  клавиатуры без касаний может заблокировать хранилище (учесть в 6.2: сообщать активность из
  полей ввода); смена «биометрия → биометрия» просит отпечаток дважды (подтверждение и запись).

## 5. Схема Firestore (3.3)

```
users/{uid}                               профиль
  schemaVersion: 2
  email: string
  displayName?: string
  createdAt: Timestamp
  crypto: {
    wrappedDek: "v2.<nonce>.<ct>"
    kdf: "hkdf-sha256"
    rkVersion: 1                          растёт при перевыпуске RK / смене DEK
    createdAt: Timestamp
  }
  items?: [...]                           данные v1 (старый ключ), до явного удаления (§6.7)
  migratedAt?: Timestamp
  deleteRequested?: true                  флаг удаления аккаунта (D4)

users/{uid}/entries/{entryId}             запись; entryId = UUID v4
  ct: "v2.<nonce>.<ct>"
  updatedAt: Timestamp (serverTimestamp)
```

- **Регистрация v2:** профиль вместе с `crypto` создаётся **одной записью** после подтверждения RK.
  Профиля «без `crypto` и без `items`» не бывает.
- **Документ на запись (D3).** **Надёжная запись (D1):** через репозиторий с `await`, ошибки явные,
  индикатор «не синхронизировано», повтор. Очередь офлайн-изменений зависит от SDK (§7).
  Реализация (6.2a): адаптер ждёт подтверждения сервера 3 с, затем сообщает `queued` (запись уже в
  офлайн-очереди SDK, повторная отправка формы создала бы второй документ). Ограничения: запись
  `setDoc` — upsert (запись, удалённая на другом устройстве, при правке создаётся снова; при
  одновременных правках побеждает последняя); отказ правил, пришедший после таймаута, до UI не
  доходит (список при следующем чтении покажет состояние сервера); запись, поставленная в очередь со
  старым DEK, не проверяется транзакцией смены ключа на другом устройстве (`rekey`, 6.4).
- **Удаление аккаунта (D4):** повторный вход → `deleteRequested: true` → удалить `entries/*` →
  удалить профиль → удалить Auth-пользователя → стереть локальные ключи (только после успеха).

**Правила v2** (деплоятся **до** миграции, задача 5.2):

```
function isOwner(uid) { return request.auth != null && request.auth.uid == uid; }

match /users/{uid} {
  allow read: if isOwner(uid);
  allow create: if isOwner(uid);
  allow update: if isOwner(uid) && (isV1Update() || isV2Update() || isRollback());
  allow delete: if isOwner(uid) &&
    (resource.data.get('schemaVersion', 1) != 2 || resource.data.get('deleteRequested', false) == true);

  match /entries/{entryId} {
    allow read, write: if isOwner(uid);
  }
}

// v1-профиль: как сейчас (в т.ч. сама миграция, которая добавляет crypto и schemaVersion: 2).
function isV1Update() { return resource.data.get('schemaVersion', 1) != 2; }

function validCrypto(c) {
  return c.keys().hasAll(['wrappedDek', 'kdf', 'rkVersion', 'createdAt'])
    && c.wrappedDek is string && c.wrappedDek.matches('^v2[.].+');
}

// v2-профиль: crypto либо без изменений, либо валидный с rkVersion+1 (перевыпуск RK / смена DEK);
// items не меняются (разрешено только удалить поле целиком); schemaVersion остаётся 2.
function isV2Update() {
  let next = request.resource.data;
  let cur = resource.data;
  return cur.get('schemaVersion', 1) == 2
    && next.get('schemaVersion', 0) == 2
    && 'crypto' in next
    && (next.crypto == cur.crypto
        || (validCrypto(next.crypto) && next.crypto.rkVersion == cur.crypto.rkVersion + 1))
    && (!('items' in next) || next.items == cur.get('items', null));
}

// Откат миграции (§6.6): снять crypto/schemaVersion/migratedAt, items целы,
// только в течение 24 ч после migratedAt.
function isRollback() {
  let next = request.resource.data;
  let cur = resource.data;
  return cur.get('schemaVersion', 1) == 2
    && 'items' in cur && 'migratedAt' in cur
    && next.get('items', null) == cur.items
    && !('crypto' in next) && !('schemaVersion' in next) && !('migratedAt' in next)
    && request.time < cur.migratedAt + duration.value(24, 'h');
}
```

(При переносе в `firestore.rules` всё это оборачивается в `service cloud.firestore { match
/databases/{database}/documents { … } }`.)

**Что правила гарантируют и чего нет:**
- После миграции v1 **не может** изменить `items` (`updateDoc({items})` отклоняется) и удалить
  профиль (`deleteDoc` без `deleteRequested` отклоняется). `updateDoc({displayName})` из v1
  проходит, это безвредно.
- **Не защищают от удаления Auth-пользователя.** В v1 «удалить аккаунт» сначала удаляет
  Auth-пользователя (`useAuth.tsx:178-181`), и это правилами Firestore не остановить. Профиль и
  `entries` останутся на сервере без владельца. Поэтому **удаление v1 со всех устройств — жёсткое
  предусловие миграции**, а восстановление из файла бэкапа в новый аккаунт (§7) работает.
- Правила проверяют **форму профиля**: либо v1 (без `crypto`, `schemaVersion` не 2), либо v2
  (`schemaVersion: 2` и валидный `crypto` с `rkVersion == 1`; переход v1 → v2 ещё и с `migratedAt`).
  Промежуточных состояний записать нельзя, поэтому аккаунт не может застрять без `crypto`.
- Откат (`isRollback`) разрешён правилами только в течение 24 ч после `migratedAt`. Приложение
  проверяет окно **до** удаления `entries` (запас 1 ч, ошибка `rollback-expired`), иначе профиль
  остался бы v2 без записей.
- Правилами не проверить, что смена DEK перешифровала **все** `entries` в той же транзакции. Это
  обязательное требование к коду и тестам (5.2: репозиторий и транзакция).
- Точный текст вычитывается и тестируется в эмуляторе Firestore (5.2), включая сценарии «откат
  проходит», «v1 updateDoc(items) отклонён», «v1 deleteDoc отклонён», «crypto без wrappedDek
  отклонён». Проект выше задаёт намерение.

## 6. Миграция v1 → v2 (3.4)

Выполняется **в приложении, на устройстве**. Запускается, когда профиль (прочитанный **с сервера**)
содержит `items` и не содержит `crypto`.

1. **Предусловия:**
   - свежий бэкап: скрипт бэкапа к этому моменту умеет выгружать `entries` (задача 5.2);
   - **жёсткое предусловие: v1 удалён со всех устройств** (приложение обновится поверх или
     переустановится). Правила (§5) блокируют запись `items` и удаление профиля из v1, но не
     удаление Auth-пользователя;
   - правила v2 задеплоены.
2. **Старый ключ:** ввод или скан старого QR. `ILegacyDecryptor` расшифровывает **все** `items` и
   проверяет форму: `title` — строка, `message` — объект со строковыми `login`, `password` и
   необязательным `description`. Это нужно, потому что CBC без MAC, и «JSON распарсился» ещё не
   значит «данные верны». Любая ошибка останавливает миграцию со списком записей, ничего не пишется.
3. **Новые ключи:** генерация RK и DEK. **До показа** RK пара `{RK, DEK, startedAt}` сохраняется в
   SecureStore как `pendingMigration`. При любом повторе используются **те же** RK/DEK, новые не
   генерируются. Если `pendingMigration` пропал (переустановка или очистка данных до коммита), а
   миграция начинается снова, приложение явно предупреждает: «ранее показанный ключ
   недействителен, сохраните новый».
4. **Показ и подтверждение RK** (текст + QR, `FLAG_SECURE`, ввод всего ключа).
5. **Атомарная запись через `runTransaction`:** транзакция читает профиль, убеждается, что `crypto`
   ещё нет, и пишет `entries/*` + `crypto`, `schemaVersion: 2`, `migratedAt`. Транзакции работают
   только онлайн. Без сети они **падают**, а не ставятся в офлайн-очередь, поэтому двух наборов
   `entries` не возникнет. Лимит операций в одной транзакции проверяется по актуальной документации
   Firestore. У нас 58 записей + 1 профиль; при большом объёме — частями с флагом незавершённости.
6. **Проверка (только чтение с сервера, `source: 'server'`):** профиль, разворот `wrappedDek`
   сохранённым RK, все `entries`, расшифровка, сравнение поле-в-поле со старыми данными (количество
   и содержимое).
   - **Совпало:** `pendingMigration` превращается в обычное хранилище ключа текущего режима, затем
     удаляется.
   - **Не совпало:** **откат**. Удалить созданные `entries` и одной записью снять `crypto`,
     `schemaVersion`, `migratedAt`. `items` не трогались. Пользователю сообщается, что данные целы
     в старом формате и миграцию можно повторить.
   - **Сбой связи между 5 и 6:** при следующем запуске профиль читается с сервера. Если `crypto` уже
     есть, а локально лежит `pendingMigration`, `wrappedDek` разворачивается сохранённым RK и
     выполняется шаг 6. Если `crypto` нет, повторяется шаг 5 с теми же ключами.
7. **`items` остаётся** в профиле (зашифрован старым ключом). Удаление — отдельное действие в
   настройках («Удалить данные старой версии»), не раньше финальной проверки в 7.3. **Старый ключ
   становится бесполезным только после удаления `items` и старых файлов бэкапа.** До этого он
   по-прежнему открывает полную копию данных v1, и это надо учитывать.
8. Новые пользователи (друзья) сразу создаются в формате v2.

Тесты (5.1/5.2): фикстура CryptoJS (`openssl enc -aes-256-cbc -md md5`), полный прогон на фейковом
`IRemoteStore`. Сценарии: «битая запись», «сбой до коммита», «коммит прошёл, ответ не дошёл»,
«проверка не сошлась → откат», «неверный старый ключ», «v1 пытается писать после миграции» (тест
правил в эмуляторе).

## 7. Бэкап из приложения (5.5, решение пользователя)

Кнопка **«Сохранить бэкап»** в настройках. Приложение выгружает JSON и предлагает место
сохранения: системный диалог Android (Storage Access Framework, например «Загрузки» или флешка)
или «Поделиться» (`expo-sharing`). Открытых данных в файле нет, как и в текущем бэкапе скрипта.

```jsonc
{
  "format": "password-manager-backup/v2",
  "exportedAt": "2026-…Z",
  "uid": "…",
  "email": "…",
  "crypto": { "wrappedDek": "v2.…", "kdf": "hkdf-sha256", "rkVersion": 1 },
  "entries": [ { "id": "<uuid>", "ct": "v2.…", "updatedAt": "…" } ],
  "legacyItems": [ … ]   // если items v1 ещё не удалены
}
```

- Перед экспортом приложение берёт данные **с сервера** и проверяет, что каждая запись
  расшифровывается текущим DEK. В файл попадает только проверенный набор, плюс итог «N записей».
- `wrappedDek` в файле означает: **файл + ключ восстановления = все данные**, даже без Firebase.
  Без RK файл бесполезен.
- **Кнопка «Загрузить бэкап» (импорт = полная замена, решение пользователя):**
  1. Выбор JSON-файла через системный диалог. Проверка формата (`password-manager-backup/v2`;
     дополнительно поддерживается файл скрипта v1 `password-manager-firestore-backup/v1` и `/v2` (скрипт; v2 добавляет `entries`) со
     старым ключом).
  2. Ключ файла: если `crypto.wrappedDek` и `rkVersion` совпадают с текущими, используется текущий
     DEK. Иначе приложение просит ключ восстановления, которым сделан бэкап (или старый ключ для v1).
  3. **Расшифровка и проверка всех записей файла** до каких-либо изменений. Любая ошибка
     останавливает импорт, текущие данные не тронуты.
  4. **Предупреждение:** «Все текущие данные (N записей) будут удалены и заменены данными из файла
     (M записей от <дата>). Это нельзя отменить». Явное подтверждение. Рядом кнопка «Сначала
     сохранить текущий бэкап», и она **предлагается по умолчанию**.
  5. Записи **перешифровываются текущим DEK** с AAD текущего аккаунта (новые UUID). Ключ
     восстановления у пользователя не меняется, файл чужого аккаунта или со старым RK тоже подходит.
  6. **Атомарная замена** (`runTransaction`): удалить все текущие `entries`, записать новые. При
     ошибке ничего не меняется. После — сверка с сервера, как в миграции (§6.6).
- `scripts/backup-firestore.mjs` дорабатывается под тот же формат (выгрузка `entries`), задача 5.2.
- **Реализация (5.5):** `updatedAt` в файле — ISO-строка или `null`; импорт защищён от дубликатов `id` и от файлов больше 8 МБ; при замене проверяется, что записи не изменились между чтением и транзакцией (`conflict`); после замены данные сверяются с сервером; при несовпадении приложение само возвращает прежние шифротексты из памяти (`rollbackImport`), и только если возврат не удался, остаётся бэкап, сохранённый перед заменой. Ограничение: запись, созданная на другом устройстве после чтения списка, транзакции не видна и не удаляется («удалить все текущие» относится к записям, известным на момент чтения).

### 8.1 `expo-secure-store` 58.0.3: результаты проверки (4.1a)

Проверено по исходникам Android-модуля и config-plugin. Адаптер: `ExpoSecureStorage` за `ISecureStorage`.

- **Класс биометрии:** `BiometricPrompt` + `CryptoObject`, проверка `BIOMETRIC_STRONG`, то есть только
  Class 3. Ключ Keystore: AES-256-GCM, `setUserAuthenticationRequired(true)` без срока действия.
  Отпечаток нужен на каждое обращение к **значению в SecureStore**, но к нему обращаются только два
  раза. При **входе** DEK читается один раз (один запрос отпечатка) и до авто-блокировки (§4) живёт в
  памяти. Записи читаются, шифруются и сохраняются этим DEK из памяти, без запросов. Второй запрос
  бывает при **включении** режима «биометрия», когда DEK записывается в SecureStore. **Решение
  пользователя: биометрия только при входе**, не при работе с записями.
- **Аннулирование при смене отпечатков:** работает (по умолчанию `setInvalidatedByBiometricEnrollment`).
  Но `getItemAsync` в этом случае возвращает **`null`**, так же как для отсутствующего ключа. При
  рассинхроне Keystore и SharedPreferences (переустановка) запись молча удаляется и тоже даёт `null`.
  Поэтому `VaultLockService` хранит текущий режим входа отдельным неаутентифицированным значением:
  «режим = биометрия, а DEK = `null`» означает «ключ аннулирован», и приложение запрашивает пароль или RK (§4).
- **Fallback на PIN устройства:** нет (только кнопка «Отмена», без `DEVICE_CREDENTIAL`). Запасной вход
  остаётся по §4: пароль приложения, если задан, иначе RK.
- **Auto Backup:** плагин прописывает `fullBackupContent` и `dataExtractionRules`, которые исключают
  `SecureStore` из облачного бэкапа и из переноса на новое устройство. Вместе с `allowBackup=false`
  (проверено после `expo prebuild`) значения SecureStore с устройства не уходят.
- **Ошибки:** отмена и сбой запроса отклоняют promise с текстом нативной ошибки. Поле `code`
  выводится из имени Kotlin-класса во время выполнения, а R8 в release эти классы переименовывает.
  Поэтому адаптер сопоставляет ошибки по тексту сообщения (строковые литералы R8 сохраняет) и
  отдаёт `AppError` с кодами `auth-canceled` / `auth-unavailable` / `secure-storage`.
- **Очистка при аннулировании:** если ключ аннулирован, следующий `setItemAsync` создаёт его заново и
  при этом удаляет **все** аутентифицированные значения под тем же `keychainService`. Поэтому у
  каждого аутентифицированного значения свой сервис `pm.auth.<key>`. Обычные значения лежат под
  `pm.plain`, эта очистка их не трогает. Удалять значение нужно с теми же опциями, с которыми его записали.
- **Отмена системой:** `BiometricPrompt.ERROR_CANCELED` (код 5: приложение ушло в фон, сенсор занят)
  приходит как `Unknown error (code: 5)`, повторный запрос — как `Authentication is already in
  progress`. Адаптер считает оба случая `auth-canceled`: тихий повтор, а не переход на запасной вход.
- **Что проверить на телефоне (5.3):** отмена запроса, сворачивание приложения во время запроса,
  блокировка после неудачных попыток, добавление отпечатка → `null`.
