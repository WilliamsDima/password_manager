## Подробно

### S1 🔴 Ключ хранится скриншотом
`KeyGen` прямо просит: «Сделайте скриншот экрана или сохраните ключ» (`ru.json: screenshot`).
Скриншот попадает в галерею, а оттуда обычно в Google Photos. Тогда и шифротекст (Firebase), и
ключ (Google Photos) лежат в одном Google-аккаунте: взлом аккаунта раскрывает всё.
Ключ также копируется в буфер обмена (`KeyGen:40`, `UserProfile:80`), выделяется как текст
(`selectable`, `KeyGen:75`) и показывается текстом и QR без `FLAG_SECURE` (см. L1).
**Сейчас:** проверить, нет ли скриншота ключа в Google Photos/облаке. Если есть, удалить из облака
и корзины, а ключ хранить офлайн (бумага, флешка) или в другом менеджере паролей.
**v2:** экран сохранения ключа с `FLAG_SECURE`, предложение записать ключ на бумаге или
экспортировать зашифрованный файл. Никаких советов делать скриншот.

### S2 🟡 PIN-экран зависит от гонки загрузки (подтвердить)
Первая версия аудита предполагала обход через таб-бар. Ревью это опровергло: `screens/Pin`
рендерит PIN внутри RN `<Modal>` (`organisms/Modal`), а это отдельное окно поверх Activity.
Нажатия до таб-бара не доходят, Back ничего не делает (`close={() => undefined}`).
Реальная слабость: экран `Pin` добавляется в стек (`main_routes.tsx:25`), только если `pin` уже
есть в Redux к моменту монтирования `TabNavigation`. Redux `user` выставляет не только `Routes`
(после чтения EncryptedStorage), но и `AuthProvider` (`onAuthStateChanged` → `getUser` →
`setUserAC`, `useAuth.tsx:138`). Если второй путь отработает раньше, стек соберётся без PIN, а
появившийся позже `pin` уже не переключит текущий маршрут. Вероятность низкая.
**Проверка:** несколько холодных стартов (особенно с хорошей сетью). Если хотя бы раз открылся
список без PIN, проблема подтверждена.
**v2:** экран блокировки как корневой gate над всем приложением. Решение «заблокировано/нет»
принимается до монтирования навигации, по умолчанию «заблокировано».

### S3 🟠 Нет авто-блокировки
`AppState` нигде не используется. PIN спрашивается только при холодном старте. Свернули
приложение, вернулись через час: всё открыто.
**v2:** блокировка при уходе в фон (с коротким настраиваемым grace-периодом) и по таймауту
бездействия; ключ в памяти обнуляется.

### S4 🟠 Слабый PIN
4 цифры (`Pin:29`), сравнение строк (`Pin:106`), лимита попыток и задержек нет. Смена PIN в
настройках (`SettingsBtns:22-26`, `createMode + settingsMode`) не спрашивает старый PIN. PIN хранится в
`EncryptedStorage` (Keystore), то есть на диске он защищён, но на уровне UI перебирается за минуты.
**v2 (решение пользователя):** режим входа на выбор: пароль приложения, биометрия (BiometricPrompt,
класс STRONG, с запасным способом входа) или без проверки. Меняется в настройках, смена и
отключение только после подтверждения текущим способом. Экспоненциальная задержка после
ошибок. В режимах с проверкой ключ данных разблокируется только после аутентификации через
Keystore (`setUserAuthenticationRequired`). В режиме «без проверки» ключ доступен любому, кто
держит разблокированный телефон; это осознанный выбор, и при включении показывается предупреждение.

### D1 🟠 Ненадёжная запись
Редьюсеры `addItem/editItem/deleteItem` (`mainAC.ts:74-100`) вызывают `updateItemAPI` без `await`
и без `catch`. При ошибке сети/правил UI показывает изменение, а в Firestore его нет. При
следующем запуске запись пропадёт. Кроме того, пока в Redux лежит Firebase `User` (у него есть `uid`,
но нет `id`, см. L4), `updateItemAPI(user.id)` падает молча. Побочные эффекты в редьюсерах вдобавок нарушают модель Redux.
**v2:** запись через репозиторий с явным результатом, индикатор синхронизации, повтор/очередь
офлайн-изменений.

### D2 🟠 Нестабильный ключ при генерации
`KeyGen:33` вычисляет `key = EncryptData(uid + +new Date().toString(), accessToken)` прямо в
теле компонента. Каждый ре-рендер (например, смена `isLoading` в `AuthContext`) даёт **новый** ключ
из-за новой случайной соли CryptoJS. Если скриншот сделан до ре-рендера, а «Сохранил» нажато после,
сохранён будет не тот ключ, что на скриншоте. В вашем случае ключ проверен (58/58), то есть
проблема не сработала.
**v2:** ключ генерируется один раз (CSPRNG, 256 бит), подтверждение вводом всего ключа перед продолжением
(CRYPTO.md §2.1).

### D3 🟡 Перезапись массива целиком
`updateItemAPI` пишет весь `items`. Два устройства или две быстрые операции подряд: последняя
запись затирает предыдущую.
**v2:** документ на запись (`users/{uid}/entries/{entryId}`) либо транзакции с версией.

### D4 🟡 Порядок операций при удалении аккаунта
`deleteUserHandler` (`useAuth.tsx:178-181`) сначала без `await` чистит `AsyncStorage` и
`EncryptedStorage` (то есть **стирает ключ**), потом удаляет Auth-пользователя, потом документ.
- Если `deleteProfile` упадёт (типично `auth/requires-recent-login`), аккаунт и данные останутся,
  а ключа на устройстве уже нет. Без внешней копии ключа данные потеряны.
- Если `deleteProfile` пройдёт, `deleteDoc` выполняется уже без авторизации и при правилах
  «только владелец» падает. Шифротекст и открытый email остаются в Firestore навсегда.

**v2:** порядок «данные → Auth → локальное хранилище», каждый шаг с `await` и обработкой
ошибки, повторная аутентификация перед удалением, подтверждение вводом.

### C1–C3 🟡 Криптография
- `crypto-js@3.3.0` (`package-lock.json`) откатил использование нативного CSPRNG, соль берётся из
  `Math.random()`. Это по истории релизов; исходники не проверены, `node_modules` нет.
- `CryptoJS.AES.encrypt(text, passphrase)`: формат OpenSSL, `EVP_BytesToKey` (MD5, 1 итерация),
  AES-256-CBC, **без MAC**. Шифротекст можно незаметно повредить или подменить.
- Ключ = `AES(uid + +new Date().toString(), accessToken)` в base64. Из-за приоритета операторов
  унарный `+` применяется к строке даты, получается `NaN`. Фактически шифруется `uid + "NaN"`,
  timestamp в ключ не входит. Непредсказуемость ключа держится на соли (64 бита из
  `Math.random`) и секретности `accessToken` (JWT в момент регистрации). Это не CSPRNG-ключ,
  хотя без токена практического перебора нет. Строка ключа содержит фиксированный префикс `U2FsdGVkX1`.

**v2:** ключ данных 256 бит из CSPRNG; AES-256-GCM (аутентифицированное шифрование) со
случайным 96-битным nonce на каждую запись; версионированный формат шифротекста
(`v2.<nonce>.<ct>`); `ILegacyDecryptor` (`CryptoJsLegacyDecryptor`) только для миграции старых данных.

### C4 🟡 Ключ при входе не проверяется
`loginHandler` (`useAuth.tsx:94`) сохраняет любой введённый ключ. С неверным ключом приложение
показывает ошибки расшифровки. Теоретически новая запись, созданная с неверным ключом, окажется
зашифрована «не тем» ключом.
**v2:** контрольное значение (зашифрованная константа/MAC) в профиле. Ключ принимается, только
если оно расшифровывается.

### L1 🟠 Нет FLAG_SECURE
`MainActivity` не ставит `WindowManager.LayoutParams.FLAG_SECURE`. Пароли, ключ и QR видны в
скриншотах, записи экрана и превью «Недавние приложения».
**v2:** `FLAG_SECURE` на всё приложение.

### L2 🟠 Буфер обмена
`ContentItem:26` копирует `"<логин> <пароль>"` одной строкой. Буфер не очищается. На Android 13+
система показывает превью скопированного текста. Фоновые приложения с Android 10 буфер не
читают, но клавиатура (IME), приложение в фокусе и облачная синхронизация буфера (у некоторых
клавиатур) имеют доступ. Логин/пароль и ключ помечены `selectable` (`ContentItem:53,58`,
`KeyGen:75`), то есть копируются в обход любой будущей авто-очистки.
**v2:** отдельное копирование логина и пароля, флаг `EXTRA_IS_SENSITIVE`, авто-очистка через
30–60 с, секреты без `selectable`.

### L4 ⚪ Токены Firebase в AsyncStorage
`KeyGen:48` вызывает `setUser(user)` с объектом Firebase `User`. Редьюсер (`mainAC.ts:35`)
пишет его в AsyncStorage через `JSON.stringify` → `User.toJSON()`, а там `stsTokenManager` с
refresh- и access-токенами. Смягчение: `allowBackup="false"`, и сам Firebase SDK тоже хранит
сессию локально.
**v2:** в хранилище только нужные поля профиля; сессией управляет SDK.

### L3 ⚪ Метаданные
В Firestore открыто: email, `displayName`, `dateCreate`, число записей, `id` = время создания
каждой записи. Для личного приложения допустимо, но в v2 `id` лучше делать случайным UUID, а даты
шифровать вместе с содержимым.

### A1 🟠 Подпись release debug-ключом
`Android/app/build.gradle:243`: `release { signingConfig signingConfigs.debug }`. Пароль
`debug.keystore` общеизвестен (`build.gradle:231-233`), а файл лежит в git. Риск зависит от того,
откуда установлена копия на телефоне:
- копия из Google Play подписана `key.jks` или ключом Play App Signing (debug-сборки Play не
  принимает), и APK с debug-подписью поверх неё не встанет;
- если стоит **собранный локально** release (с debug-подписью), любой может собрать APK с той же
  подписью и поставить его «обновлением» поверх.
Ответ пользователя: **на телефоне стоит версия из Google Play**, то есть подписанная ключом Play
App Signing. Наличие `private_key.pepk` говорит, что, скорее всего, в Play загружался собственный
ключ подписи (`key.jks`), но это нужно сверить по SHA-256 (см. «Что сделать сейчас»). От этого зависит, получится ли ставить v2 поверх без удаления.
**Проверка:** `apksigner verify --print-certs <apk>` на установленном APK
(`adb shell pm path com.eclipse.account_manager` → `adb pull`). Сравнить с `key.jks` и
`debug.keystore`. Данные всё равно в Firestore, поэтому в худшем случае приложение просто
переустанавливается и ключ вводится заново.
**v2:** release подписывается только собственным ключом. Пароли keystore хранятся в
`~/.gradle/gradle.properties`, не в репозитории.

### F1 🔴 Firestore открыт всем (подтверждено 2026-11-25)
Правила в консоли: `match /{document=**} { allow read, write: if true; }`. Без входа, по одному
`projectId` (он есть в APK) любой может:
- прочитать все документы `users/*`: шифротекст, email, имена, даты;
- **перезаписать или удалить** любые данные, включая ваши записи.

Пароли без ключа не прочитать, но данные можно уничтожить или подменить. Шифротекст без MAC (C2)
не позволяет надёжно обнаружить подмену. Бэкап от 2026-11-25 расшифрован ключом 58/58, то есть
на момент бэкапа данные были целы.
**Исправление:** [`firestore.rules`](../firestore.rules), доступ только владельцу к `users/{uid}`,
всё остальное запрещено. Совместимо с v1.

### F2 Firebase
**v2:** правила в репозитории (`firestore.rules`) + App Check (Play Integrity / debug provider

### F3 ⚪ API-ключ без ограничений, открытая регистрация
Скрипт бэкапа (фаза 1) вошёл через Identity Toolkit REST из Node с ключом из
`src/config/firebase.ts`, то есть ключ не ограничен. Для Firebase **JS SDK**, на котором работает
v1, это штатная ситуация: JS SDK не передаёт заголовки `X-Android-Package`/`X-Android-Cert`.
**Ограничение по Android-приложению (пакет + SHA-1) сломает v1.** API-ключ Firebase не секрет,
доступ к данным решают правила. Реальный риск в другом: любой может регистрировать аккаунты в
вашем проекте и перебирать пароль входа.
**Решение пользователя:** регистрацию оставляем открытой: приложением могут пользоваться друзья.
Поэтому изоляция пользователей держится только на правилах (F1), и они обязательны. В v2 стоит
рассмотреть защиту входа от перебора (Firebase Auth уже ограничивает частоту попыток) и App Check.
Ключ можно ограничить по списку API (Identity Toolkit, Token Service, Cloud Firestore), это
безопасно и для v1, и для скрипта бэкапа.
**v2 (5.4):** ограничение по Android-приложению имеет смысл только при переходе на нативный SDK
(`@react-native-firebase`); вместе с App Check (F2).

4. **S2:** при случае понаблюдать, не открывается ли список без PIN после холодного старта.

## Входные требования для фаз 3–5

Из аудита следуют обязательные требования к v2:
- ключ 256 бит из CSPRNG, AES-256-GCM, версионированный формат, проверка ключа контрольным значением;
- ключ на устройстве в Android Keystore, разблокировка биометрией/PIN, лимит попыток;
- корневой экран блокировки, авто-блокировка при уходе в фон, `FLAG_SECURE`;
- безопасный буфер обмена с авто-очисткой;
- надёжная запись (явные ошибки, без перезаписи всего массива) и безопасный порядок удаления аккаунта;
- миграция v1 → v2 с проверкой 100% записей до удаления старого формата;
- правила Firestore в репозитории, только владелец; ограниченный API-ключ; release подписан собственным ключом;
- без рекламы, лишних разрешений, cleartext-трафика и логов в release.
